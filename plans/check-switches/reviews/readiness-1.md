## Findings

**B1 — D3, D3(b), V1.2, V2.6: health dedup key unspecified; a natural choice makes V1.2/V2.6 unreachable.** `Alerts.health` keys the outbox row by `health:<kind>:keccak(dedup)` and `enqueue` uses `INSERT OR IGNORE` (`alerts.py:227-233, 80-86`). With `dedup = "check-disabled:<id>"` the second disable of V1.2 is dropped; with `dedup = …:<block>` the disable → enable → disable with no new block of V2.6 is dropped (same checkpoint). Same for `check-enabled` keyed by block B. Fix: D3 states the dedup = `check-disabled:<id>:<n>` / `check-enabled:<id>:<n>` where `n` is a per-check disable counter kept in the D7 marker (incremented per enabled → disabled transition); V1.2 and V2.6 assert the counter.

**S1 — D7/D9, V1.2: who clears the disabled marker when there is no catch-up.** D3's "once" is marker-based, so V1.2's second notice needs the marker cleared at the re-enabling start. D7 never says so; D9 clears it only when a catch-up record is written (`backfill.enabled` true, phase live) or when the global silent run commits (phase backfill); nothing covers `backfill.enabled: false` (the harness, V2.2(d)). Fix: D7 adds "`bootstrap()` clears the marker of every built check (CP1)"; D9 refines it (record written → clear; phase backfill → clear on silent-run commit; `backfill.enabled` false → clear at bootstrap, no record) and V2.2(d) asserts the marker is gone.

**S2 — D11 wording excludes unregistered built checks.** "every registered check id that has a cursor or marker row, built or not" read literally drops the rewind for built-but-unregistered stubs (`test_scheduler_reorg_resets_event_cursor` uses `Stub`, id `stub`, not in `REGISTRY`: `test_framework.py:681-700`), the very control V1.4 names. Also `_cursor()` returns a default when no row exists (`:276-277`), so "no row created for ids without state" needs an explicit row test. Fix: D11 = "built checks as today, plus every id with an existing `cursor:events:<id>` or `reorg:<id>` meta row" (iterate `meta` keys, not `REGISTRY`).

**S3 — V1.7, V2.7, PF-04: red-on-base runs will be red for the wrong reason.** `test_switches.py` will import the new registry helper and read `status["disabled"]` / `status.checks.<id>.catchup`; on `9e94a1a` the module fails at collection (ImportError) or at a KeyError before the behavioural assertion.
